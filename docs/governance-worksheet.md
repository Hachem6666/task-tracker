## 5.3B: Dockerfile Traced Line by Line

| Line(s) | What it does | Why it is there | What could break | Do I own this yet? |
|---|---|---|---|---|
| `# ---- Builder stage ----` / `FROM python:3.11-slim AS builder` (lines 1–2) | Starts a first, temporary build stage named `builder`, based on the slim Python 3.11 image. | This is a **multi-stage build**: the point is to do the "messy" work (installing build tools, compiling packages) in one image, then throw that image away and copy only the finished result into a clean final image. `slim` is used instead of the full `python:3.11` image to keep size down while still having a usable Debian base (unlike `alpine`, which can cause issues with some Python C-extension packages). | If you remove `AS builder`, line 18 (`COPY --from=builder ...`) has nothing to reference and the build fails outright. If you change the Python version here without changing it in the runtime stage below, you can get subtle version mismatches between build and run environments. | Partially |
| `WORKDIR /app` (line 4) | Sets `/app` as the current directory inside the builder stage for all subsequent instructions. | Keeps files in a predictable, non-root location rather than littering `/`. `/app` is a common convention, not a requirement. | If removed, subsequent `COPY`/`RUN` commands would operate relative to the image's default working directory (`/`), which still works but is messier and less conventional — unlikely to "break" anything by itself. | Yes |
| `COPY requirements.txt .` (line 6) | Copies just `requirements.txt` from your machine into `/app` in the builder image. | Copying *only* the requirements file before the rest of the source code is a deliberate Docker layer-caching trick: as long as `requirements.txt` doesn't change, Docker can reuse the cached "pip install" layer even when your app code changes, making rebuilds much faster. | If this line were removed, the `pip install -r requirements.txt` on line 9 would fail (no file to read). If you instead copied the whole repo here (e.g. `COPY . .`), you'd lose the caching benefit — every code change would force a full reinstall of all dependencies. | Yes |
| `RUN pip install --no-cache-dir --upgrade pip && pip install --no-cache-dir --prefix=/install -r requirements.txt` (lines 8–9) | Upgrades `pip` itself, then installs all dependencies from `requirements.txt` into `/install` instead of the normal system site-packages location. | `--no-cache-dir` avoids storing pip's download cache in the image layer (keeps image smaller). `--prefix=/install` redirects the install target so that line 18 can cleanly copy *just* the installed packages into the runtime stage, without also dragging in pip itself, build caches, or anything else that landed in the builder's normal Python paths. | If you drop `--prefix=/install`, packages install to the default location, and line 18's `COPY --from=builder /install /usr/local` would copy nothing — the runtime image would be missing all dependencies and `uvicorn` would fail to start. I have not verified end-to-end that `--prefix=/install` reliably places console scripts (like `uvicorn`) on `PATH` after the copy — it usually works on Debian-based images since `/usr/local/bin` is on `PATH` by default, but this specific build wasn't tested by me. | Partially |
| `# ---- Runtime stage ----` / `FROM python:3.11-slim` (lines 11–12) | Starts a **second, fresh** image, also based on `python:3.11-slim`, discarding everything from the builder stage except what's explicitly copied over. | This is the actual image that ships/runs. Using the same base as the builder avoids glibc/library mismatches between what packages were built against and what they run against. | If this used a different base image or Python version than the builder, installed packages (especially any with compiled C extensions) could fail to import at runtime with cryptic errors. | Partially |
| `RUN useradd --create-home --shell /bin/bash app` (line 14) | Creates a new non-root Linux user named `app`, with a home directory and bash as its shell. | Security best practice: containers that run as `root` by default are a bigger blast radius if the app is ever compromised. Running as an unprivileged user limits that. | If removed, line 21 (`USER app`) would fail because the user wouldn't exist. `--shell /bin/bash` is a minor, non-load-bearing nicety — not actually needed for `uvicorn` to run. | Partially |
| `WORKDIR /app` (line 16) | Sets `/app` as the working directory in the runtime stage (a fresh image, so this has to be re-declared). | Same rationale as the builder's `WORKDIR` — a new stage has its own filesystem. | Same as above — low risk if removed, just less conventional. | Yes |
| `COPY --from=builder /install /usr/local` (line 18) | Copies the installed Python packages from the builder stage's `/install` directory into `/usr/local` in the runtime image. | This is the actual "keep only what we need" step of the multi-stage build — brings in installed dependencies without any build-time tooling, pip cache, or the `requirements.txt` copy. | If removed, none of the app's dependencies would exist in the final image, and `CMD` would fail immediately with `ModuleNotFoundError` or "uvicorn: command not found". | No |
| `COPY app ./app` (line 19) | Copies the local `app/` directory (application code) into `/app/app` in the runtime image. | Only `app/` is copied — not `tests/`, `frontend/`, or `docs/` — keeping the runtime image minimal, working together with `.dockerignore`. | If removed, there's no application code in the image, and `uvicorn app.main:app` would fail with `ModuleNotFoundError: No module named 'app'`. Changing this to `COPY . .` would risk shipping `.env` or `.git` if `.dockerignore` isn't airtight. | Yes |
| `USER app` (line 21) | Switches the effective user for all remaining instructions (and the running container) from `root` to `app`. | Enforces the non-root-runtime security posture — without it, the `useradd` on line 14 would create a user that's never actually used. | If removed, the container runs as `root`. I have not re-checked `docs/security-review.md` in this session to confirm whether it specifically flags this. | Yes |
| `EXPOSE 8000` (line 23) | Documents that the container listens on port 8000. | `EXPOSE` is metadata only — it does not publish the port. It's a hint for humans/tools (e.g. `docker run -P`). | Removing it doesn't break the app; the actual binding happens via `--port 8000` in `CMD`. You still need `-p 8000:8000` on `docker run` for the port to be reachable — `EXPOSE` alone doesn't do that. | Yes |

## 5.3C: Personal AI Usage Rules

### Rule 1 – Never paste sensitive information into AI tools

Before I paste anything into an AI tool, I will check that it does not contain passwords, API keys, customer data, or other confidential company information. If I'm unsure whether something is sensitive, I'll remove or replace it with sample data before using AI, even if I'm under time pressure.

### Rule 2 – What I will always verify before accepting AI output

Before I accept AI-generated code or explanations, I will test the result myself and make sure I understand how it works. If I can't explain a piece of code or I'm not confident it's correct, I'll check the official documentation or another reliable source before using it. I will also review any screenshots or outputs to make sure they don't contain confidential or identifying information before sharing them.

### Rule 3 – How I will record AI contributions

I will keep a simple record of any significant work generated with AI, including what AI helped create and what I changed or verified myself. For more complex or important parts that I don't fully understand, I will add a more detailed review, such as a line-by-line explanation or trace, and mark whether I fully understand it, partially understand it, or still need to review it. This way, I can clearly show which parts I have verified and which ones need more learning before I rely on them.
